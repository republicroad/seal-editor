# BP-02：哨兵测试模式

## 适用场景

你的系统**依赖了某个第三方库的当前行为**，但该行为未被上游文档承诺为 API 契约（属于实现细节）。如果上游升级后行为变化，你的系统会静默出错。

## 核心模型

用测试将当前行为钉死：如果上游升级导致行为变化，测试先红——强制你在升级前评估影响，而非在生产中发现。

| 要素 | 说明 |
| --- | --- |
| 被钉住的行为 | 第三方库的内部实现细节 / 未文档化的副作用 / 性能特征 |
| 断言 | 当前行为的精确描述（不是"应该怎样"，而是"现在怎样"） |
| 触发 | 上游 patch/minor 升级后自动运行，行为变化 → 先红 → 强制评估 |

## 铁律

1. **测试注释必须说明"这是哨兵"**——与普通回归测试区分；红不一定是 bug，是行为变化信号
2. **只钉有下游影响的行为**——纯内部实现细节不值得钉
3. **行为变化不等于要修**——需要评估影响后决定：接受新行为 + 更新哨兵，或锁定旧版本

## 参考实例

zen-udf 单一源（jdm-editor 仓；2026-09-28 ruling 12 后移出本仓，本仓经 npm 消费 `@republicroad/zen-udf`）：

- `packages/zen-udf/src/engine-cache-semantics.test.ts`：钉住 zen-engine 2.0.2 的四条缓存语义（函数 loader 无引擎缓存 / getDecision 绕过 / createDecision 可复用 / customNode 不影响缓存）
- 升级 zen-engine 后测试红 → 需重新评估 L1 缓存设计（多租户设计文档 §3 的前提条件）

## 反模式

| 反模式 | 后果 |
| --- | --- |
| 哨兵测试红了直接改绿（适应新行为）不评估影响 | 潜在的静默行为变化流入生产 |
| 钉住太多无关行为 | 升级时大量无关红测试增加维护成本 |
| 只测 happy path 不测副作用 / 错误形状 | 漏掉关键的错误处理行为变化 |
